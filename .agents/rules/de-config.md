# DEV Execution Rules
기능 구현 및 개발 작업을 진행할 때, 다음 문서들의 가이드라인과 규칙을 항상 최우선으로 읽고 설계 및 구현에 반영하세요:

@/ragUnityTestGuide.md
@/Integrationplan.md
@/ragSystemplan.md



# [DEV 개발 모드 작동 규칙]
이 규칙은 사용자가 "코드 진행해줘", "개발 시작해줘", "기능 구현해줘" 등의 개발 지시를 내렸을 때 활성화됩니다.
## 초강력 원칙: 선(先) 계획, 후(後) 개발 (No Code Without plan.md)
어떤 상황에서도 코드(.cs)부터 수정하지 마세요.
요구사항을 받으면 가장 먼저 프로젝트 루트에 대표 작업 이름을 담은 plan.md를 작성(또는 업데이트)하고, 사용자의 최종 컨펌(승인)을 얻은 뒤에만 실제 코드 작업에 착수해야 합니다.

## 계획서 파일 생성 규칙
저장 경로: 프로젝트 루트의 plans/ 폴더 내부 (폴더가 없다면 새로 생성)
파일명 규칙: plan_[영문_작업_스네이크_케이스].md
예시: "로그인 기능 구현" 요청 시 -> plans/plan_login_feature.md 생성
예시: "차량 이동 버그 수정" 요청 시 -> plans/plan_fix_car_movement.md 생성

1. DEV Constraints (개발 제약 조건)
C# 코드 수정 허용: 기능 구현, 버그 해결, 리팩터링 등을 위해 Unity C# 소스 코드(.cs)를 자유롭게 수정하고 개선할 수 있습니다.
계획서 필수: 코드 수정 전 반드시 아래의 plan.md 템플릿에 맞추어 작업 계획을 수립하세요.
테스트 지향 개발: 기능 구현 시 기존 가이드(@ragUnityTestGuide.md)에 따라 테스트 가능성(Testability)을 고려하여 코드를 작성하세요.
2. Linear & GitHub Synchronization Rules
GitHub 상태 확인: 작업을 마친 후, 반드시 git status 및 git diff 명령을 실행하여 의도한 파일(C# 및 plan.md)만 수정되었는지 교차 검증하세요.
Linear 자동 업데이트: 작업 완료 후 python tools/sync_linear_with_code.py 스크립트를 실행하거나 Linear API를 활용하여 관련 PBI 이슈를 'Done' 상태로 자동 업데이트하고 상세 구현 내용을 반영하세요.
3. Code Template (plan.md)
개발 작업을 시작할 때 생성해야 하는 표준 템플릿입니다.
Markdown
# 📌 작업 계획서: [대표 작업 이름 작성]

## 1. 개요 및 목표
* 이번 작업으로 해결하려는 최종 목표를 한 줄로 요약합니다.

## 2. 주요 작업 단계 (대표 작업 리스트)
- [ ] **Step 1: [첫 번째 대표 작업 이름]**
  - 세부 태스크 1
  - 세부 태스크 2
- [ ] **Step 2: [두 번째 대표 작업 이름]**
  - 세부 태스크 1
- [ ] **Step 3: [세 번째 대표 작업 이름]**
  - 테스트 및 검증 시나리오 작성

## 3. 예상 예외 사항 및 제약 조건과 코드 구현이유
* 작업 중 발생할 수 있는 병목이나 주의해야 할 기술적 제약 사항을 기술합니다.
* 이렇게 코드 작업진행할 명확한 기준을 제시합니다.
* 명확한 기준을 작성하면 장점과 단점을 1가지 명확하게 작성합니다.

## 4. 완료 정의 (Definition of Done)
* 무엇이 완료되면 이 작업이 끝났다고 볼 수 있는지 명확한 기준을 제시합니다.
4. DEV 완료 정의 (Definition of Done)
작업을 마친 후 아래 체크리스트를 모두 만족해야 비로소 작업이 최종 완료된 것으로 간주합니다.
[ ] 작성한 plan.md 파일의 모든 작업 단계 체크박스가 [x]로 업데이트되었는가?
[ ] 수정된 Unity C# 소스 코드와 plan.md가 GitHub에 함께 정상적으로 커밋 및 푸시(Push)되었는가?
[ ] 수정된 기능에 대해 자체 검증(또는 빌드/테스트 에러가 없는지)을 확인했는가?
[ ] Linear PBI 이슈가 자동으로 업데이트 및 닫기('Done') 상태가 되었는가?
