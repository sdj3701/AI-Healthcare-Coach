# 카메라·관절 추적 수명주기 복구 Plan

## 1. 목적과 현재 증상

이 작업은 iOS 실기기에서 카메라 미리보기와 관절 좌표를 같은 화면 좌표에 정확히 표시하고, 사용자가 화면과 버튼을 어떤 순서로 조작하더라도 카메라와 MediaPipe 추적기가 다시 시작될 수 있게 만드는 것이 목적이다.

현재 해결해야 할 증상은 다음 네 가지다.

1. 사용자가 화면 오른쪽에 있으면 관절이 왼쪽에 표시되고, 중앙에서만 일치한다.
2. `START -> STOP -> START` 이후 두 번째 추적이 시작되지 않는다.
3. 리셋 또는 다른 화면으로 이동한 뒤 세션 화면에 다시 들어오면 카메라가 복구되지 않는다.
4. 전면·후면 카메라 전환이 완료되지 않거나, 전환 뒤 추적이 재개되지 않는다.

## 2. 진단 결과

### 2.1 좌우가 반대로 표시되는 원인

- `videoVerticallyMirrored`는 카메라 픽셀 메모리의 상하 배치를 보정하는 값이고, 전면 카메라의 셀피식 좌우 반전과는 다른 정보다.
- 현재 UI는 카메라 이미지 자체에 회전·상하 반전을 적용하면서 같은 `Image`의 `generateVisualContent`에 관절도 그린다.
- MediaPipe 결과는 이미 회전과 픽셀 상하 배치가 보정된 분석 영상 좌표인데, UI에서 관절에 카메라 원본용 변환을 다시 적용한다.
- 전면 카메라 표시를 위한 `x = 1 - x` 규칙이 명시되어 있지 않다. 이 때문에 중심점 `x = 0.5`만 우연히 일치하고 좌우 비대칭 위치는 반대로 보인다.

### 2.2 재시작이 실패하는 원인

- `StopTracking()`은 추적 요청을 취소하지만, 이미 실행 중인 비동기 MediaPipe 요청은 native callback이 끝날 때까지 물리적으로 남을 수 있다.
- 그 사이 다시 `StartTracking()`을 누르면 기존 coroutine이 있다는 이유로 새 시작을 반환하고, 이전 요청 종료와 새 시작의 소유권이 명확하지 않다.
- UI는 `IsRequestInFlight`만 최대 1초 기다린다. 추적 loop 종료, 카메라 첫 유효 프레임, 실제 카메라 facing 변경까지는 확인하지 않는다.
- 따라서 빠른 Stop/Start 또는 카메라 전환에서 이전 세대의 완료 신호가 새 세션 상태를 덮어쓸 수 있다.

### 2.3 화면 전이 뒤 카메라가 복구되지 않는 원인

- 목표 수정·운동 선택은 추적만 중지하고 카메라는 유지하지만, 리셋은 카메라까지 중지한다.
- 세션 화면에 들어갈 때 카메라를 반드시 준비하는 단일 진입 절차가 없다.
- 결과적으로 같은 세션 화면이라도 어떤 버튼으로 이동했는지에 따라 카메라 상태가 달라지는 비결정적 흐름이 된다.

### 2.4 전·후면 전환이 실패하는 원인

- 현재 전환은 `Stop -> 선호 facing 토글 -> 두 프레임 대기 -> Start`로 구성된다.
- 두 프레임은 AVFoundation 해제 완료를 보장하지 않으며, 새 카메라의 첫 유효 프레임이나 실제 `isFrontFacing` 값을 확인하지 않는다.
- 카메라가 준비되기 전에 추적과 버튼 잠금을 복구하므로, UI는 전환된 것처럼 보이지만 내부는 아직 정지 또는 시작 중일 수 있다.

## 3. 구현 규칙

코드 작업은 아래 규칙을 순서대로 지킨다.

1. **좌표 계약을 하나로 고정한다.** Provider 결과는 `분석 완료된 upright 정규화 좌표`로 유지한다. 카메라 원본 표시 보정과 관절 표시 보정을 분리하고, 전면 카메라일 때만 카메라와 overlay에 동일한 좌우 미러 정책을 적용한다.
2. **카메라 이미지와 관절 overlay를 분리한다.** 카메라 `Image`에는 WebCamTexture 회전·상하 배치 보정과 셀피 미러를 적용하고, 형제 overlay에는 최종 fitted rect 기준 관절 좌표만 그린다. 관절이 카메라 원본 변환을 두 번 받지 않게 한다.
3. **고정 프레임 대기를 준비 조건으로 사용하지 않는다.** 카메라 시작·전환은 `HasValidFrame`, 목표 facing, timeout을 확인하고 완료한다.
4. **추적 요청에 세대 번호를 둔다.** Stop은 현재 세대를 무효화하고, 이전 세대 callback은 UI·최신 프레임·새 세션 상태를 바꾸지 못하게 한다.
5. **재시작 요청은 유실하지 않는다.** 이전 추적 loop/request가 정리 중일 때 Start가 들어오면 `restart requested` 상태로 남기고, 정리가 끝난 직후 정확히 한 번 시작한다.
6. **세션 화면 진입 경로를 하나로 만든다.** 세션 화면을 렌더링하거나 START를 누르면 같은 `EnsureCameraReady` 절차를 사용한다. 화면 이탈 방식과 무관하게 재진입 결과가 같아야 한다.
7. **일반 STOP에서는 무거운 native graph를 폐기하지 않는다.** MediaPipe 인스턴스는 재사용하되, 요청 세대와 busy 상태만 안전하게 정리한다. 앱 종료·컴포넌트 파괴에서만 dispose한다.
8. **전이 잠금은 `finally`에서만 해제한다.** 성공·실패·timeout 어느 경우에도 버튼이 영구 잠기지 않게 하고, 실패 메시지를 UI와 로그에 남긴다.

## 4. 구현 단계

### 단계 A — 표시 좌표 복구

- `MobileWorkoutPrototypeView`의 preview와 pose overlay를 형제 `VisualElement`로 분리한다.
- preview의 fitted rect를 단일 계산 함수에서 구해 두 요소에 공유한다.
- 카메라 preview에는 rotation, `videoVerticallyMirrored`, 전면 셀피 미러를 적용한다.
- overlay는 upright fitted rect에 그리며 전면 카메라에서만 landmark X를 반전한다.
- replay에는 카메라 실시간 metadata를 적용하지 않는다.

### 단계 B — 추적 Stop/Start 상태 안정화

- `JointTrackingController`에 lifecycle generation과 restart queue를 추가한다.
- `StartTracking()`은 정리 중이면 시작 의도를 보존하고, 중복 coroutine은 만들지 않는다.
- `StopTracking()`은 세대를 증가시켜 이전 결과를 폐기하고 provider 취소를 요청한다.
- estimate 완료 시 요청 세대를 검사해 오래된 결과와 오류를 무시한다.
- UI가 기다릴 수 있도록 `IsStopping` 또는 `IsIdle` 성격의 상태를 노출한다.

### 단계 C — 카메라 시작·전환 API 통합

- `CameraCaptureSource`에 카메라 준비를 기다리는 coroutine/API를 추가한다.
- facing 전환은 CameraCaptureSource가 한 작업으로 소유한다: 기존 세션 중지, settle delay, 원하는 facing 선택, 시작, 첫 유효 프레임, 실제 facing 검증.
- 전·후면 중 한 종류만 있는 기기에서는 timeout 대신 명확한 실패 사유를 반환한다.
- 새 카메라 texture가 생기면 이전 frame/update 캐시를 무효화한다.

### 단계 D — UI 화면 전이 통합

- 세션 화면 진입과 START가 공통 `EnsureSessionCameraReady` 흐름을 사용하게 한다.
- Reset은 세션 데이터와 replay만 초기화하고 카메라를 불필요하게 종료하지 않는다. 카메라를 종료해야 하는 경로가 생기더라도 재진입 시 반드시 Ensure 절차로 복구한다.
- 목표 수정·운동 선택·Reset·전환 중에는 추적을 먼저 정지시키고, 요청 정리가 완료된 뒤 화면 또는 카메라 상태를 바꾼다.
- 카메라 전환 중 운동 중이었다면 새 카메라 첫 유효 프레임 확인 후에만 TTS와 추적을 재개한다.

### 단계 E — 회귀 검사

- 기존 에디터 QA에 좌표 매핑과 수명주기 계약 검사를 추가한다.
- C# 컴파일 오류, Unity 직렬화 변경, iOS native bridge 시그니처 호환성을 확인한다.
- 변경 파일 diff를 검토해 unrelated 수정이 포함되지 않게 한다.

## 5. 장점과 단점

### 장점

- 전면·후면 및 회전 metadata가 바뀌어도 카메라와 관절이 동일한 위치에 표시된다.
- 빠른 버튼 입력과 오래 걸리는 native callback이 겹쳐도 이전 세션이 새 세션을 덮어쓰지 않는다.
- 화면 전이와 카메라 전환이 같은 준비 조건을 사용해 재현하기 어려운 간헐 오류가 줄어든다.
- MediaPipe graph를 매번 재생성하지 않아 재시작 지연과 iOS 메모리 부담을 줄인다.

### 단점

- preview와 overlay를 분리하면서 UI 레이아웃 코드가 조금 늘어난다.
- 상태 세대와 준비 timeout을 추가하므로 lifecycle 코드가 기존보다 명시적이고 길어진다.
- Unity 에디터만으로 실제 iPhone의 모든 AVFoundation timing을 재현할 수 없어 최종 실기기 반복 검증이 필요하다.

## 6. 검토한 대안

1. **Provider의 모든 X 좌표를 무조건 반전**: 구현은 간단하지만 후면 카메라까지 뒤집고 replay/다른 소비자 좌표 계약을 깨므로 사용하지 않는다.
2. **현재 한 Image 구조에서 landmark를 raw texture 좌표로 역변환**: 요소 수는 유지되지만 0/90/180/270도와 상하 반전 조합의 역변환이 복잡하고 재발 가능성이 높아 사용하지 않는다.
3. **Stop마다 MediaPipe를 Dispose/Initialize**: 상태는 초기화되지만 시작 지연, GPU graph 생성 비용, iOS crash 위험이 커 일반 Stop에는 사용하지 않는다.
4. **카메라 전환 시 몇 프레임만 기다리기**: 구현은 짧지만 기기 성능과 AVFoundation 해제 시간에 의존하므로 `첫 유효 프레임 + facing 확인 + timeout` 방식으로 대체한다.
5. **모든 화면에서 카메라를 계속 실행**: 재진입은 빠르지만 배터리·발열·개인정보 표시 비용이 있다. 이번 범위에서는 세션 전이 중 불필요한 재시작을 피하고, 세션 진입 시 준비를 보장하는 절충안을 사용한다.

## 7. 완료 기준

- 전면 카메라에서 사용자가 화면 왼쪽·중앙·오른쪽으로 이동할 때 관절이 같은 쪽을 따라간다.
- 후면 카메라에서도 좌우가 일치하고, portrait 상태에서 회전 오류가 없다.
- `START -> STOP -> START`를 10회 반복해 매번 새 관절 프레임이 들어온다.
- 운동 선택/목표 수정/리셋 후 `1 -> 2 -> 3` 화면으로 돌아와 START를 누르면 카메라와 추적이 시작된다.
- 추적 중과 정지 중 각각 전·후면 전환을 10회 반복해 실제 facing이 바뀌며, 추적 중이었다면 자동으로 재개된다.
- 전환 버튼을 빠르게 눌러도 버튼이 영구 정지하지 않고 crash가 발생하지 않는다.
- 에디터 QA와 프로젝트 컴파일 검사가 통과한다.

## 8. 구현 결과

- 단계 A: preview와 pose overlay 분리, 전면 카메라 X 미러 및 회전별 raw preview 변환 적용 완료.
- 단계 B: tracking epoch, Stop 중 Start handoff, native cancel-drain 및 recovery budget 초기화 적용 완료.
- 단계 C: 목표 facing 사전 검사, 첫 유효 프레임/실제 facing 검증, 실패 시 이전 카메라 복구 적용 완료.
- 단계 D: 명시적 PreviewMode, camera-ready 후 운동 시작, 비동기 화면 이탈, Reset/Replay 상태 정리 적용 완료.
- 단계 E: Runtime/Editor C# 컴파일 및 Unity 결정론 QA 통과.
- 남은 실기기 검증: Mac Xcode에서 Swift/MediaPipe 컴파일 후 이 문서 7절의 반복 시나리오를 iPhone에서 수행한다.
